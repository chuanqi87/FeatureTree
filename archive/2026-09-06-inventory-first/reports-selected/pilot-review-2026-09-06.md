## 结论

准备代码和有限试跑已完成本轮改进，但**当前不能宣称具备全面分析的全部条件，也没有启动全量**。研究输入可用；正式版本基线、代表性知识试点验收仍未闭环。三个证据草稿不能替代三个已完成研究的节点，更不是通过验收的五个试点。

本轮没有新增 confirmed 知识，没有人工真机测试。当前树仍为 212 节点（106 叶子、106 汇总），5088 个必要支持/比较槽位尚未评估。此分母不含未来新增 facts；当前树也不代表三个 SDK 的全部能力。

## 发现的问题与已完成的修改

1. **任务过大，时间消耗在规范和结构处理上。** 新交接命令默认先做 evidence 报告；通过独立阅读复核后，再以 candidate 阶段处理单节点内 3–5 个指定知识项。任务包固定模型、范围和输入指纹，禁止修改未选中的陈述、通过共享上下文影响其他知识项，或删除既有事实。此次实跑验证了报告粒度可交付；新的小批次候选机制有回归测试，但尚没有真实知识的生产验收通过记录。
2. **来源路径和长哈希人工转录不可靠。** 新增来源导出命令，从资料库核对正文和原始响应哈希后，导出随 Git 保存的精选快照。本次三个报告的 17 个来源条目已自动校正路径、正文哈希和获取时间；其中包含弱证据/目录页，不能把 17 份快照说成 17 份已充分论证的结论。来源快照不自动获得版本确认。
3. **实际发生了语义过度概括。** 后台报告把 Android Q+ SDK 的“可以指定服务类型”写成“必须”；已按 `Service.startForeground` 正文拆开 SDK、target SDK 与 Android 14+ 条件。分布式报告从 Swift Distributed 的传输抽象推断 iOS 没有对应总线，此否定推断已撤回；HarmonyOS 的 801 约束也改为具体方法/条件，不再覆盖整个模块。
4. **正式版、手机和真机边界混杂。** Android Cross device SDK Preview 移到预览附录，不能作为正式方案主比较；Wearable 测试放入非手机附录；模拟器只能预检查，不计人工真机完成。iOS 候选筛选也增加显式 visionOS/macOS 等非 iOS 路径排除，避免空 availability 元数据漏拦。
5. **规则变化后沿用旧成果的风险。** 研究说明、Schema 与校验代码纳入任务和预检查指纹。旧包保留用于追溯，不能修改它来掩盖输入变化。交付存在、结构通过、语义复核、正式采纳分别记录，检查工具从不自动合并正式知识。
6. **粒度建议也需要复核。** UI 草稿建议拆四个节点，但不同文档主题不自动构成不同特性。修订后以“状态到界面的一致性”为主，其他内容优先进入既有维度；有独立用户任务和可观察结果时才提新节点。本轮没有机械修改特性树。

## 启动前仍要完成什么

**版本基线。** 已读取官方发布材料并保存调查记录，但没有用猜测创建 `baseline.json`。Android、iOS 已找到正式版候选及 SDK 依据；HarmonyOS 已找到消费手机正式主线材料，具体手机系统与 API/SDK 的配对仍缺闭环。开发套件 Release 不等于消费手机系统正式推送，系统、SDK、工具版本也不能按相同数字拼接。详见 [版本调查](../research/baseline-investigation.json)；这份调查不是启动基线。真正启动日必须重新核实最新正式版及设备条件，不能沿用试跑日期代替。

**知识生产验收。** 五个代表性试点仍需按小批次完成全部指定比较项、逐条证据与评级，再由独立复核者验收。调查后的 unknown 可以保留，但必须有具体调查说明和缺口；不允许只写一份报告就把整节点标为完成。先验证少量真实、可确认陈述能从证据走到候选、复核、展示，再补齐代表性节点。没有降低既有启动门槛，也没有伪造 `pilot-review.json`。

**覆盖边界。** 当前还有 201 个节点需审查排除范围，一个绑定正文缺口，以及目录中的未映射/范围待定项。这些进入研究清单；不要求靠机械补字段“清零”，也不承诺当前树覆盖全部 SDK。分布式节点尤其需要先补 iOS 的场景框架和 Android 正式方案，而不是要求用户先写自定义传输或先买设备。

## 最终交付应是什么

| 交付物 | 用户能据此做什么 | 不应误解为 |
| --- | --- | --- |
| 逐条知识卡与三平台差异矩阵 | 看支持范围、7 个比较维度、关键事实、官方明示/分析区分、版本、条件与来源 | 每个平台都有答案，或找不到就是不支持 |
| 置信度与真机需求双轴 | 按高/中/低/未评估，及必须/建议/无需真机筛选 | 高可信等于已经实测；低可信必然要买设备 |
| 可按预算导出的复核清单 | 选择领域、节点与知识项数量，取得具体机型条件、操作步骤、预期和缺口 | 导航祖先也被选中，或未选范围自动算完成 |
| 带前提的洞察与缺口清单 | 看差异的含义、来源知识项、限制和未覆盖分母 | 用未知前提得出平台排名、独有或完全等价 |

评级是定性证据判断，不是未经校准的“95%正确”。高可信也可以同时必须真机复核：对官方契约有把握，但目标手机运行行为尚待验证。低可信的静态缺口应优先补文档；只有运行时序、后台存活、设备差异等需要真实观测的问题进入真机用例。

建议的完成口径：**在你选定的特性树范围内完成文档研究，诚实保留未知；人工只执行你选择的高风险/高价值复核项。** 未执行的必测项保留待验证，不影响查看其他已有证据的知识，但限制相关洞察的措辞。默认先叶子、再汇总；不将全部机型、全部 SDK 或所有实测都当作这轮必达范围。

OpenCode 负责有界的证据研究和候选整理；独立复核负责解释、版本和跨平台比较的准确性。并行先控制在两个不同节点，不自动重试或换模型。范围导出工具已经支持知识项预算；当前没有评级时，不能用空的“必须真机”清单证明没有实测工作。
